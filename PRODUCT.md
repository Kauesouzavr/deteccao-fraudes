# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

Primary: technical recruiters and hiring managers screening the project
owner's portfolio (confirmed — owner wants the GitHub repo public
"para recrutadores verem meu projeto"). They land on the dashboard from a
link (résumé, LinkedIn, GitHub profile) and skim in under a minute, with no
prior context on the dataset or the owner's work.

Secondary: the owner themselves, using the live dashboard as a visual aid
while explaining the project out loud in an interview or technical
conversation (inferred from how the build process unfolded — the owner
asked for a "live, testable" demo specifically to show, not just a static
report).

## Product Purpose

A public, deployed dashboard that demonstrates applied ML + full-stack
engineering skill through a real, reproducible project: detecting credit
card fraud on the public Kaggle "Credit Card Fraud Detection" dataset. It
exists to be evidence of capability, not a production fraud-detection
service (confirmed — the owner directed that limitation be documented
explicitly on the dashboard's underlying repo).

Success = a recruiter understands, within a skim, that the owner can (1)
run a rigorous ML pipeline (preprocessing, multiple models, cross-validation,
hyperparameter tuning, a documented balancing-strategy comparison) and (2)
ship it as a real, live, deployed product — not just a notebook.

## Positioning

Most student/portfolio ML projects stop at a Jupyter notebook or a static
write-up of metrics. This one ships as a deployed web product with a model
that runs live in the visitor's own browser (the trained Random Forest's
decision trees are exported to JSON and walked in TypeScript — no backend,
no server cost, no cold starts) — the mechanism itself (client-side
inference of a real trained model) is the differentiator, not just the
reported accuracy numbers.

## Operating Context

- Visited via a public URL (currently a Vercel `*.vercel.app` domain), no
  login, no account system.
- Viewed cold by a stranger (a recruiter) with zero onboarding — nothing can
  assume the visitor already knows what "undersampling" or "F1-score" means.
- Also used actively by the owner during a live conversation/interview as a
  talking-points aid — content needs to support being pointed at and
  narrated over, not just read silently.
- Data is pre-computed (static JSON snapshots from local Python runs) except
  for the one interactive predictor, which computes live in-browser.
- Source lives in a monorepo: Python ML pipeline at the repo root, Next.js
  dashboard in `web/`. The dashboard is the only visitor-facing surface;
  the Python side is implementation detail, not something recruiters open.

## Capabilities and Constraints

- Next.js 16 (App Router) + React 19 + Tailwind CSS v4, deployed on Vercel's
  free/Hobby tier. No database, no auth, no backend API routes in current
  use — stay on Hobby-tier-compatible, zero-ops infrastructure unless the
  owner explicitly asks to add a backend.
- All displayed metrics/charts come from a single static JSON file
  (`web/public/dados/resultados.json`), regenerated by local Python scripts
  and committed to the repo — not computed at request time.
- The in-browser predictor only lets the visitor adjust `Valor` (amount) and
  `Horário` (time) of a real example transaction; the other 28 features
  (V1–V28) are anonymized PCA components with no editable real-world
  meaning — this is a hard constraint of the dataset, not a UI choice to
  "fix" later.
- Confirmed, explicit limitation the product must keep surfacing honestly:
  trained and validated on one public dataset only; not a production fraud
  system. This is already written into the repo's README and should not be
  softened or hidden by a visual redesign.
- Portuguese (pt-BR) is the content language throughout; no i18n requirement
  established.

## Evidence on Hand

Real, already-computed results exist and must be preserved, not
invented: per-model accuracy/precision/recall/F1 (main pipeline + 5-fold
cross-validation with std dev), a hyperparameter-tuning before/after
comparison, an undersampling-vs-SMOTE comparison evaluated against the
dataset's real (imbalanced) class distribution, confusion matrices, top-10
feature importances per model, and a sample of real test-set transactions
with per-model predictions. No testimonials, customer logos, or benchmarks
exist or should be fabricated.

## Product Principles

1. **Numbers are real and must stay traceable** — every stat on the
   dashboard maps to an actual script/output in the repo; redesign changes
   presentation, never the figures or their honest framing (including the
   documented dataset limitation).
2. **Skim-first, narrate-second** — a recruiter with 60 seconds and zero
   context must get the headline result at a glance; an interviewer walking
   someone through it needs clean handoff points between sections.
3. **No invented production weight** — the product is an honest portfolio
   piece, not a fake SaaS; professional/trustworthy visual language should
   not imply live production fraud monitoring that doesn't exist.
4. **Zero-ops by default** — prefer solutions that keep the project
   deployable on Vercel's free tier with no backend/database, matching how
   it already runs (e.g. the client-side model predictor).

## Brand Commitments

No existing logo, name beyond "Detecção de Fraudes", or locked color
identity. The owner has directed a visual-world change toward a
"professional, like a bank/fintech site" register (requested during this
session) — this is a binding visual constraint to resolve in `new-work`,
not expanded here.

## Accessibility & Inclusion

No specific standard required by the owner. No known constraint beyond
standard web accessibility practice (contrast, keyboard operability for the
interactive predictor's range inputs).
